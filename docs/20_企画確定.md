### 1.5 徒歩transferのコストと生成方針（P-8の根拠）

doc12 3.4節が定める「直線距離上限800mの徒歩transfer事前計算」を実データで見積もった結果、同4章のシャード予算（都道府県3MB以下・バックボーン2MB以下）と**両立しないことが判明した**。サイズは1024基準（MiB）で示す。

| 方式 | ペア | 事業者跨ぎ | 接続事業者ペア | 概算サイズ | 都道府県平均 |
|---|---:|---:|---:|---:|---:|
| 素の800m（doc12 原設計） | 1,713,091 | 569,643 | 1,371 | **91.5MB** | 1.95MB |
| 半径300mへ縮小 | 371,517 | 123,825 | 1,217 | 19.8MB | — |
| 半径100mへ縮小 | 122,822 | 43,371 | 1,071 | 6.6MB | — |
| 20m名寄せのみ・800m | 663,228 | 179,646 | — | 35.4MB | 753KB |
| **20m名寄せ＋上限K=8（採用）** | **353,073** | **66,582** | **1,318** | **18.9MB** | **411KB** |

**確度**: 800mの3指標（ペア総数・事業者跨ぎ・接続事業者ペア）は2つの独立実装（`measure_merge_effect.py` / `xfer800.py`）で完全一致した**確定値**。他は単一実装。

素の800mでは**熊本4.5MB・高知4.0MB・長野3.5MB・三重3.2MBがtransferだけで3MB予算を超過**する。東京圏はODPTに都道府県属性が無く「(不明)52.4MB」に含まれるため実際はさらに悪い。これは`stops`・`routes`・`trips`・`stopTimes`を載せる前の数字である。

**半径縮小ではなく上限Kを採る理由**:

1. **エッジの偏りが小さい**。最大次数202・中央次数14、上位1%の停留所が占めるエッジは6.0%・上位10%でも35.6%。爆発は一部の高密度停留所ではなく全体に薄く広がっており、半径縮小は全体を一律に削ることになる。
2. **疎な地域の損失が大きい**。**800m以内に他事業者の停留所が無い停留所が87,070件（57%）**ある。他事業者接続を持つ65,751停留所のうち最近傍が300m超は31.2%・500m超は16.6%。半径300mにすると約31%の停留所が他事業者への乗換を失う。上限K方式は疎な地域でも「最も近いK件」を必ず保持するため、**交通空白地域を主対象とする本プロダクトでは損失が構造的に小さい**。
3. **同サイズで優る**。半径300m（19.8MB・事業者ペア1,217）より20m名寄せ＋K=8（18.9MB・1,318）が上。

**名寄せは新しい経路を生まない**点に注意する。近接停留所は名寄せしなくても徒歩transferで接続されるため（`packages/router`の`relaxTransfers`は実装済み）、名寄せの効果はノード数削減（152,821→104,231、**31.8%削減**）とUX（同一地点が「乗換」と表示されるのを防ぐ）と、本節のサイズ削減である（doc17 C-25）。

再現: `python3 data/_scripts/xfer800.py` / `python3 data/_scripts/xfer_policy.py`

## 3. 企画の骨格: 3つの締切【実装】

既存の経路検索は所要時間・運賃・乗換回数を最適化する。過去9年の受賞作（doc04）も一貫して「行ける経路をどう良く見せるか」だった。本作品は**「間に合わなかったときに何が起きるか」**を主役にする（P-1）。

柱ごとに、由来するGTFSフィールド／公開型のどこに乗るか／実装済みか／非スコープとの関係を確定させる。

### 3.1 柱①: 予約締切

| 項目 | 内容 |
|---|---|
| 由来フィールド | `stop_times.pickup_type` / `drop_off_type` / `pickup_booking_rule_id` / `drop_off_booking_rule_id`、`booking_rules.txt`（`prior_notice_duration_min` / `prior_notice_last_day` / `prior_notice_last_time` / `phone_number` / `message` / `info_url`） |
| 公開型 | `TransitLeg.boardingRequirement` / `alightingRequirement`（`phone_agency` / `coordinate_with_driver`）、`TransitLeg.booking`（`BookingInfo`）、`ItinerarySummary.requiresBooking`、`FlexLeg.booking` |
| 実装状況 | **実装済み**（doc17 T-26・C-24解決、2026-08-28）。テストT-RAPTOR-06〜15・T-API-06〜07。実データ3市町で検証済み |
| 非スコープとの関係 | 衝突なし |
| 残作業 | **routerは完了。** 残るのは表示側（`apps/web`）のみ: 予約制定時便の締切・連絡先の表示と、締切・連絡先を持たない20フィードの文言（doc17 T-27） |

締切超過時の扱いはFlexレッグと**意図的に非対称**にした。Flexは締切超過レッグを枝刈りするが、定時便は捨てずに締切情報を添付して残す（doc13 6.4節）。時刻表に載っている便を結果から消すと利用者は「そんな便は無い」と受け取るため、締切を示して代替を案内する（doc15 4.4節・P-10）。

対象は§1.2の27フィード・962便。うち20フィードは締切・連絡先が無いため、§2.3の表示方針に従う。

### 3.2 柱②: 帰りの門限

「この目的地に行くなら、何時までに帰り始めないと帰れないか」を主表示にする。

| 項目 | 内容 |
|---|---|
| 由来フィールド | `stop_times`（時刻）＋`calendar.txt` / `calendar_dates.txt` |
| 公開型 | 新規。`ItinerarySummary`ではなく別APIとして切る（§5.2） |
| 実装状況 | 未実装 |
| 非スコープとの関係 | **doc13 1.2節 NS-1（到着時刻指定の逆探索）を踏まない**。下記の方法で回避する |

**逆探索を実装しない方法（P-4）**: `plan()`に`arrivalTime`を渡すのではなく、**目的地→出発地の向きで出発時刻を二分探索**する。

```
門限 = max{ T | plan(目的地→出発地, departureTime = T) が経路を返す }
```

早く出発すれば待てば済むため、実現可能性は`T`について**単調減少**する。よって二分探索が正当である。`plan()`は1回0.4〜1.1ms（`packages/router/PERF.md`）なので、11〜15回の探索で約15ms。`arrivalTime`パラメータも時間反転RAPTORも使わないため、doc13の改訂は不要。

根拠となる実データは§1.3（平日の最終発が17時前の停留所24.42%）。

### 3.3 柱③: 乗換失敗のリカバリ時間

「この乗換に失敗すると、次は何時間後か」をレッグごとに示す。既存アプリは「乗換2分」を都市部と同じ顔で出すが、平日2便以下の停留所が10,630あり（§1.3）、そこでの2分は「失敗したら数時間後、または翌日」を意味する。

| 項目 | 内容 |
|---|---|
| 由来フィールド | `stop_times`（同一停留所の次便までの待ち時間） |
| 公開型 | `TransitLeg`に「次便までの秒数」を添付 |
| 実装状況 | 未実装 |
| 非スコープとの関係 | **doc13 NS-2（GTFS-RT非対応）に触れない**。遅延データを使わず、静的時刻表上の「次便までの待ち時間」として定義する。実際に遅延したかは扱わない |

「失敗」を遅延で定義すると NS-2 に当たる。**静的計算で表現できる指標に限定する**：(a)次便までの待ち時間 (b)その乗換を逃すと当日中に目的地へ到達できなくなるか。(b)は柱②と同じ仕組みで求められる。
